Mission delivery plan

Groundloop

A staged plan for making daily AI-assisted development current, relevant, cumulative and measurably better without adding unnecessary ceremony.

Mission: Make AI-assisted development improve every day: keep project understanding current, apply it to the work at hand, and turn daily experience into simpler, proven ways of working.

Plan date: 22 July 2026 - first dogfood environment: a local multi-repository workspace - portable package before public distribution

Implementation checkpoint — 22 July 2026: the portable alpha now implements Phases 0–4: database-free status and checkpoints, post-session operational lesson fingerprints, Codex/Claude launchers with a startup-only hook, dual plugin manifests, daily reflection, improvement scouting, installation lifecycle, diagnostics, privacy-filtered digests and baseline/treatment comparison. Learning runs only after the launched agent process closes; no per-tool or prompt-time hook runs during work. Phase 5 scheduling remains gated on five useful manual reflections; Phase 6 dogfood has begun.

1. Mission outcomes

Start current

Every session can state what is known, what changed, how fresh that understanding is and where attention is needed.

Work relevantly

Only the conventions, examples, lessons and delivery expectations that matter to the current work are brought forward.

Improve daily

Daily experience produces a justified enhancement, a focused exploration, a verification result or an explicit no-change outcome.

North-star outcome: over time, the workspace becomes easier to understand, safer to change and simpler to operate, while the developer spends less effort reconstructing context and repeating solved work.

Recommended cadence

  • Every session: quick startup status.
  • Every task: relevant guidance through normal agent and skill selection.
  • Once each working day: evidence-led reflection in proposal mode.
  • Weekly or on demand: improvement scouting.
  • Continuously: verify prior improvements when enough evidence exists.

Opt-in comparison

Groundloop is launched as an explicit treatment rather than silently changing every agent session. The developer can alternate between the same underlying work configuration with and without grounding:

# Baseline
codex -p work
claude

# Groundloop treatment, preserving all trailing CLI arguments
codex-ground-loop
claude-ground-loop

The launchers record only the host, workspace identity, Groundloop variant and timing fields needed for the trial. They do not fork the developer's model, permission or tool configuration. Comparisons are directional workflow evidence, not claims of a controlled scientific experiment.

Four small capabilities

  1. Status: maintain an honest, cheap view of freshness and due work.
  2. Reflect: capitalise on daily lessons and patterns.
  3. Scout: seek an occasional step-change when evidence exposes an opportunity.
  4. Verify: determine whether adopted improvements delivered value.

The capability core is host-neutral. Codex and Claude adapters translate lifecycle input and output, while workspace adapters describe repositories and conventions. MCP is not required to prove this design. A later MCP can expose the same proven capabilities to remote hosts without moving the product's rules or state into the MCP layer.

5. Session-start summary

Skills themselves use progressive disclosure: their metadata is discovered at startup and full instructions load only when invoked. The hook therefore does not load or run a full skill. It runs a fast Groundloop status command, displays the result and gives the agent the same factual context.

Summary contract

GROUNDLOOP - CURRENT
Workspace: 4/4 repos known | remote refs checked 07:42
Drift: 2 repos changed since last grounding | working tree dirty
Daily reflection: current - 21 Jul 18:10
Improvement: 1 proposal awaiting verification
Scout: next due 25 Jul | last leap reviewed 18 Jul
Skills: reflection available | scout available

Status vocabulary

StatusMeaningUser implication
CURRENTConfigured repositories, local state, skill availability and daily reflection are within their freshness thresholds.Continue normally.
CHANGESSources are fresh, but meaningful repository or workspace changes occurred after the previous grounding.The agent should incorporate the delta for the task.
STALERemote refresh, reflection or skill validation is overdue.Refresh before making broad project claims.
PARTIALOne or more configured repositories or sources could not be checked.Proceed with the named limitation.

Freshness definition

  • Local repository HEAD and working-tree state are checked when the hook runs.
  • Remote freshness reports the time of the last successful bounded fetch; it is never inferred from a local ref alone.
  • Daily reflection is current when a successful review covers the previous 36 hours.
  • Skill availability confirms the shared source and client-discoverable links are present and last validation passed.
  • Previous improvements show a due date rather than being silently forgotten.

Hook requirements

  • Run for startup, resume, clear and compact lifecycle events where supported.
  • Complete the local check within two seconds under normal conditions.
  • Stay below eight lines and roughly 900 characters.
  • Perform no reflection, web research or unbounded repository traversal.
  • Fail open with a concise PARTIAL summary.
  • Return no secrets, environment dumps, source contents or transcript text.
  • Use one cross-platform Groundloop status command with thin Claude and Codex output adapters.

Launcher contract

  • codex-ground-loop sets the Groundloop treatment marker and delegates to codex --profile work --dangerously-bypass-approvals-and-sandbox --dangerously-bypass-hook-trust by default. The configured profile name is overridable at install time without duplicating flags.
  • claude-ground-loop sets the same marker and delegates to claude --dangerously-skip-permissions while preserving the developer's normal arguments.
  • Both are executable shims on PATH, not shell-specific aliases, so argument forwarding, updates and Windows/macOS/Linux behaviour can be tested consistently.
  • The Groundloop aliases intentionally provide unattended execution and must be used only in a trusted workspace where unrestricted access is intended. Plain codex -p work and claude retain their normal permission behaviour.
  • Claude uses its session-only plugin loading where practical. Codex uses an installed hook that exits immediately with no output when the marker is absent. This keeps codex -p work and plain claude as meaningful operational baselines while acknowledging that the trial is not laboratory isolation.
  • The treatment marker lets the reflection distinguish Groundloop sessions without modifying or parsing prompts.
Cross-agent implementation note: current Claude Code and Codex both support SessionStart events for startup, resume, clear and compact. Claude accepts startup context through stdout or additionalContext. Codex supports model-visible SessionStart hook output and ordinarily requires project hook trust; the explicitly unrestricted Groundloop alias bypasses that trust prompt. Hook output and model-context behaviour are covered by the dual-host smoke tests.

6. Skill design

reflect-on-development

Purpose: evidence-led daily improvement from internal development activity.

Cadence: daily, after difficult work, or on request.

Sources: privacy-filtered threads, Git delta, failures, tests, evidence, existing guidance and prior proposals.

Primary outcome: incremental improvement and verification.

scout-development-improvements

Purpose: recommend a high-leverage skill, technology, practice or learning topic that could create a meaningful step-change.

Cadence: weekly, on demand, or when reflection identifies an unresolved opportunity.

Sources: current project needs, local skill inventory, primary technical sources, official documentation and relevant current research.

Primary outcome: one evidence-fitted leap experiment.

Why two skills

DimensionDaily reflectionImprovement scout
QuestionWhat did our work teach us?What could materially improve how we work?
DirectionInside-out: project evidence to improvement.Outside-in: opportunity to relevant external option.
BiasIncremental, maintain and simplify.Exploratory, step-change and learning.
FrequencyDaily.Weekly or triggered.
OutputDecision register and verification.Leap proposal and experiment.

Their short descriptions are visible at startup; their full instructions load only when selected. This separation improves triggering without adding normal context weight.

Update: reflect-on-development

  1. Replace the rolling-window-only model with a last-successful-review checkpoint plus a 36-hour fallback.
  2. Include repository changes since the last reviewed commit for every configured workspace repo.
  3. Review open improvement proposals and decide whether evidence supports keep, adjust, consolidate or retire.
  4. Add an exploration gate: send unresolved high-value opportunities to the scout rather than doing broad research inside the daily review.
  5. After a Groundloop-launched agent process closes, correlate sanitised command failures, warnings and subsequent corrections into operational lesson fingerprints; track recurrence, resolution, relevance and retirement without retaining complete commands.
  6. Keep lesson analysis out of active sessions. Reflection decides whether evidence warrants a helper, preflight, regression test, linter or concise guidance.
  7. Prioritise one daily improvement. Keep the existing limit of at most five material lessons and three actions.
  8. Advance the checkpoint only after a complete report is produced.

Operational lesson lifecycle

failure or warning → sanitised fingerprint → correction → recurrence check
                   → watch | automate | promote | retire

A one-off typo normally expires. Two independent occurrences, or one severe preventable incident, can become shared guidance or automation. Startup shows only an active count; detailed analysis remains in the post-session reflection workflow and never interrupts the task in progress.

New: scout-development-improvements

Proposed description:

Research and recommend one high-leverage skill, technology, engineering
practice, or learning topic grounded in current development evidence.
Use when daily reflection exposes an unresolved improvement opportunity,
during a weekly improvement scan, or when the user asks how to make the
development workflow materially better.

Scout workflow

  1. Select one opportunity from current evidence or an explicit user question.
  2. State the desired improvement and current constraint.
  3. Check existing workspace skills, scripts and installed capabilities before suggesting something new.
  4. Research current options using primary and official sources wherever available.
  5. Compare adopt, integrate, extend, build and learn paths.
  6. Recommend one option and at most two alternatives.
  7. Define a small reversible experiment, expected value, cost, success signal and stop condition.
  8. Produce a self-contained HTML proposal; do not install or change the workspace without explicit authorisation.

Scout output contract

  • Opportunity and evidence.
  • Why it could produce a step-change.
  • Recommended skill, technology, practice or topic.
  • Fit with the current workspace.
  • What existing capability it reuses or replaces.
  • Experiment and measurement.
  • Risks, cost and exit path.
  • Review date.

8. Delivery roadmap

Phase 0 - Mission, baseline and contracts 2-3 days

Mission support: define what “current,” “daily,” “simpler” and “proven” mean before implementation.

Work

  • Approve the mission and three outcomes as the decision filter.
  • Inventory workspace repositories and their configured baseline refs.
  • Capture one week of baseline session warm-up, repeated friction, delivery omissions and current reflection effort.
  • Define baseline and treatment launch contracts: codex -p work versus codex-ground-loop, and plain claude versus claude-ground-loop.
  • Define a host-neutral core contract, host adapter contract and optional workspace configuration schema before choosing packaging technology.
  • Define status, reflection, scout and verification output contracts.
  • Define privacy-safe source fields and retention.

Exit criteria

  • At least ten representative session/task scenarios.
  • Every proposed plan item maps to a mission outcome.
  • No implementation begins without a measurable baseline.

Phase 1 - Groundloop status core 3-5 days

Mission support: make current project understanding visible and honest.

Work

  • Create a bounded, portable project configuration for repositories, baseline refs, guidance sources and freshness thresholds.
  • Create a cross-platform status core with stable human and JSON output; keep platform-specific process and path handling behind adapters.
  • Track last successful remote refresh, reviewed commit, report timestamps, skill validation and due verifications.
  • Use atomic state updates in a per-user Groundloop data directory keyed by workspace identity, not inside the product repository.
  • Add focused fixtures for current, changed, stale, partial, dirty and rewritten-history states.

Exit criteria

  • Status is accurate across all configured repositories.
  • Normal local execution completes within two seconds.
  • State can be deleted and rebuilt safely.
  • No secret-bearing source is read or printed.

Phase 2 - Daily reflection closes the loop 3-5 days

Mission support: turn daily experience into practical improvements and verify previous ones.

Work

  • Update reflect-on-development with checkpoint, verification and scout-routing steps.
  • Add launcher-owned, post-session failure fingerprints, correction correlation, recurrence thresholds and retirement to the soft ledger without per-tool hooks.
  • Add previous-proposal review to the HTML report contract.
  • Record the exact repository cutoffs covered by each successful report.
  • Keep reports decision-led and accept an empty improvement result.
  • Validate the skill and refresh its Codex/Claude metadata and links.

Exit criteria

  • Three consecutive real daily reviews complete without duplicate or invented lessons.
  • At least one previous improvement receives an evidence-based verification decision.
  • The next review starts from the previous successful cutoff.

Phase 3 - Cross-agent SessionStart summary 2-4 days

Mission support: begin every session with current, concise orientation.

Work

  • Create one startup-status script that consumes SessionStart JSON and calls the status core.
  • Add thin Claude and Codex output formatting only where their contracts differ.
  • Create codex-ground-loop and claude-ground-loop launchers that preserve arguments, use the developer's existing configuration, enable Groundloop only for that process and apply each host's explicit unattended permission-bypass mode.
  • Package shared skills, status command and host-specific hooks behind Codex and Claude plugin manifests from one source tree.
  • Install user-level, treatment-gated hooks without placing helpers in product repos.
  • Test startup, resume, clear and compact events in both clients.
  • Confirm the summary is visible to the user and available to the model.

Exit criteria

  • Eight-line summary appears correctly in both clients.
  • Current, changes, stale, partial and hook-failure cases are distinguishable.
  • Hook failure never prevents a session from starting.
  • No full skill body, thread digest or network research runs from the hook.
  • Baseline commands produce no Groundloop summary; treatment launchers use the same underlying model, permission and work configuration.

Phase 4 - Improvement scout skill 3-5 days

Mission support: create deliberate opportunities for step-change improvement.

Work

  • Initialise scout-development-improvements with the standard skill creator.
  • Keep SKILL.md concise; use a reference only for the comparison and proposal rubric.
  • Generate Codex UI metadata and make the shared skill available to Claude.
  • Test triggers that distinguish reflection from scouting.
  • Run three real scout scenarios: suggest a skill, evaluate a technology and propose a learning topic.

Exit criteria

  • Every scout output is grounded in a current workspace opportunity.
  • It recommends one bounded experiment rather than a technology list.
  • It checks existing capabilities before proposing a new skill or tool.
  • No installation or workspace change occurs in proposal mode.

Phase 5 - Scheduling and verification cadence 2-3 days

Mission support: make improvement daily and self-checking without relying on memory.

Work

  • After five successful manual runs, schedule the daily reflection in proposal mode.
  • Run the scout weekly or only when a high-value unresolved opportunity is queued.
  • Include open verification dates in startup status and daily reports.
  • Keep scheduled work at workspace scope and read-only unless separately authorised.
  • Review the first five scheduled runs and tune cadence/output.

Exit criteria

  • Daily review runs reliably on working days or reports why it did not.
  • Scout does not run merely to fill a weekly report.
  • Every adopted enhancement has a follow-up date and success signal.

Phase 6 - Thirty-day dogfood evaluation 30 days

Mission support: prove that the loop creates meaningful daily value.

Work

  • Use Groundloop across at least twenty real development sessions and retain a comparable set of baseline sessions.
  • Compare matched task categories across launcher cohorts for time to confident work, repeated investigations, delivery omissions and improvement adoption.
  • Review false/stale startup claims and irrelevant reflection/scout proposals.
  • Calculate maintenance effort against conservatively estimated time saved.
  • Decide continue, narrow, absorb into existing skills or stop.

Exit criteria

  • Mission metrics meet the gates in section 9.
  • The workflow remains useful after novelty fades.
  • A clear decision is made before MCP or publication work begins.

Phase 7 - Productisation decision gated

Mission support: expand access only if it preserves the proven experience.

Possible next step

  • Promote the already dogfooded dual-host package into Codex and Claude marketplace distribution.
  • Publish one installer with install, init, doctor, update and uninstall lifecycle commands.
  • Add a small MCP only if multiple hosts need live shared status or action interfaces.
  • Publish registry metadata only after external alpha users return voluntarily.
  • Keep code-intelligence and document systems composable rather than rebuilding them.

Evaluation scenarios

  • Resume after a day with new commits on multiple develop branches.
  • Start from a feature branch with dirty changes.
  • Daily reflection after no material work.
  • Repeated script or local environment failure.
  • A failed command followed by a correction, then a similar task in a later session.
  • Recurring PR evidence or ticket-link omission.
  • Verify a previously adopted test, script or skill improvement.
  • Scout an existing skill before proposing a new one.
  • Scout a current technology with a plausible workflow benefit.
  • Scout a learning topic that could remove a recurring capability gap.
  • Operate when a repository, network or hook component is unavailable.
  • Run baseline and Groundloop launchers with identical forwarded arguments and confirm only the treatment receives Groundloop context.
  • Install, initialise, diagnose and uninstall in a clean Windows, macOS and Linux test workspace without modifying a product repository.

Workspace footprint

Default: no files are written into the workspace. groundloop init discovers bounded Git repositories and stores a private configuration under the user data directory. A team may explicitly choose groundloop init --shared to create one reviewable project file such as .groundloop/project.yaml; generated state, reports and thread-derived data remain outside product repositories.

One-command onboarding target

# Package-manager or signed release installation; exact channel chosen in Phase 0
<install groundloop>

groundloop install --hosts codex,claude --codex-profile work
cd <workspace>
groundloop init
groundloop doctor

codex-ground-loop
claude-ground-loop

install registers or locates the dual-host plugin, creates launch shims and validates host versions. init configures project sources. doctor proves hook visibility, permissions, state rebuildability and baseline isolation. uninstall removes only Groundloop-owned files and registrations.
