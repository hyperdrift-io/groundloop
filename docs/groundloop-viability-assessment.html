Mission and product architecture

Groundloop

A daily continuity and improvement companion for developers working with AI across changing projects and repeated sessions.

Mission: Make AI-assisted development improve every day: keep project understanding current, apply it to the work at hand, and turn daily experience into simpler, proven ways of working.

1. Why Groundloop

AI-assisted development is powerful inside a session but weak between sessions. The project moves, the working context disappears, and valuable lessons remain scattered across code, conversations, documentation and individual habits.

The developer pays the difference by repeatedly explaining the project, rediscovering operational knowledge and remembering how work is expected to be delivered.

The continuity gap is not a lack of information. It is the failure to bring the right understanding to the right piece of work, and to make today's experience improve tomorrow's development process.

2. User and job

The first user is a developer who works with AI agents every day, moves between sessions or repositories, and owns more context than can be re-established efficiently each time.

Core job

When I begin or resume development work, help me become productively grounded without re-explaining the project, then help the way I work improve from what we learn.

The desired feeling

The AI collaborator should feel less like a new contractor arriving every morning and more like a strong returning teammate: aware of what changed, respectful of how the project works, and able to build on prior experience.

3. Product promise

Start informed

Understand what is current, what changed, what matters for the task and where reliable answers live.

Stay aligned

Apply the project's architecture, conventions, recurring patterns and delivery expectations while the work is happening.

Improve daily

Review what was learned, propose practical enhancements, and explore relevant approaches when the best improvement is not yet known.

These are the product's three outcomes. Every capability must make at least one materially better.

Ground

Connect the session to the current project: meaningful change, active context, relevant intent and trusted sources.

User value: quicker confidence and less re-orientation.

Guide

Bring forward the conventions, examples, checks and prior lessons that matter to the work at hand.

User value: fewer wrong turns and more consistent delivery.

Improve

Review recent work, recognise repeated friction, propose practical enhancements and explore relevant technology or practice when evidence reveals a gap.

User value: experience compounds instead of disappearing.

One improvement path

What the daily review findsGroundloop response
A lesson with a clear solutionPropose the smallest useful enhancement and where it belongs.
A recurring problem without a clear solutionExplore focused alternatives, compare them against the project and recommend a next experiment.
A related technology or practice that may helpResearch it only in relation to the evidenced opportunity and state the expected value.
No material lesson or opportunityRecord no improvement. Daily review does not require daily change.
The loop is the architecture. Groundloop is valuable when better grounding improves work, and the experience of that work improves future grounding and practice.

6. Knowledge and source strategy

Groundloop treats the project as a living body of knowledge rather than equating knowledge with code alone.

Project reality

  • Code, tests and configuration
  • Architecture and product documentation
  • Scripts, templates and delivery checks
  • Repository and workspace instructions

Development experience

  • Decisions and their rationale
  • Recurring failures and successful resolutions
  • Evidence and validation outcomes
  • Explicitly relevant tickets, PRs and design documents
  • Related technology and practices explored for a specific improvement opportunity

External documents

Documents belong in the product model whenever they materially shape the work. They do not need to become a separate product pillar.

Initially, the developer or an existing workflow exposes the relevant ticket, design, PR or runbook. Groundloop uses it alongside the rest of the project context. Broader document integration becomes worthwhile only when a recurring source is important enough that manual exposure repeatedly breaks the experience.

Source access should grow from user value. Start with the sources already present in the development workflow. Add deeper access only where it noticeably improves grounding, guidance or learning.

EffortlessThe benefit should exceed the attention and maintenance Groundloop asks from the developer.
ComposableGroundloop uses the strongest available project and agent capabilities without requiring one tool ecosystem.

Product priority test

A proposed capability belongs in Groundloop when it clearly improves one of these:

  1. Time to confident work.
  2. Alignment with the project's way of working.
  3. Prevention of repeated friction.
  4. The project's ability to improve from experience.

If the user cannot feel the improvement in one of those outcomes, it is not a product priority.

9. Personal validation before product development

The first version should test the mission, not an implementation architecture.

Thirty-day experiment

  1. Observe one week of normal sessions: time spent re-orienting, repeated explanations, recurring friction and delivery omissions.
  2. For the next three weeks, use a lightweight Groundloop workflow to begin work, prepare delivery and run one daily improvement review.
  3. Review whether the three promises - start informed, stay aligned, improve daily - became noticeably true.

Continue only if

  • At least 20 real sessions provide enough evidence.
  • Time to confident work falls meaningfully, with 30% as the working target.
  • At least three repeated investigations are avoided or shortened.
  • At least two lessons become durable improvements that remain useful.
  • Targeted exploration produces useful options without becoming unfocused technology scouting.
  • The workflow is used voluntarily in at least 70% of eligible sessions by the end.
  • The perceived value clearly exceeds the effort required to maintain it.
Current decision: worth testing for personal use. Not yet justified as a public project. The experiment is successful even if Groundloop is not built, provided it reveals a smaller workflow, skill or practice that delivers the value more simply.

Skill strategy

Use one improvement workflow. The existing reflect-on-development skill should own daily review, lesson consolidation, enhancement proposals and evidence-triggered exploration. A separate research skill is justified only if focused technology evaluation later becomes a substantial reusable workflow in its own right.

10. Path forward

  1. Personal practice: prove that the Ground-Guide-Improve loop creates daily value.
  2. Shared workflow: make the same experience work naturally across Claude and Codex.
  3. Composable product: connect the best available code, document and recall capabilities where they strengthen the mission.
  4. MCP distribution: package the proven experience for discovery and use by other developers.
  5. Community project: publish only when people return to it because it improves their work, not because the idea sounds promising.

Relationship to existing tools

Codebase Memory MCP and codebase-context deepen understanding of current code and conventions. Rekal preserves historical intent. Groundloop's mission is to turn the most relevant understanding and experience into a better development session and a better way of working.

MCP is therefore a future delivery and discovery surface, not the reason Groundloop exists. The product should earn the right to become an MCP by proving the loop first.
